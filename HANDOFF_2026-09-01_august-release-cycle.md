## Incident — M8 release email sent 3x (2026-09-01)

The M8 email reached the Release Notes audience (`97c42e60-...`) three times:

| Broadcast id | Sent (UTC) |
|---|---|
| `24d3b577-ed9d-44f1-8813-598e5b989420` | 2026-09-01 20:06:41 |
| `1ba676ea-fc2f-432b-95a6-2d5d7a437c24` | 2026-09-01 20:20:22 |
| `207174b2-0576-4718-83ec-5db95bdfa332` | 2026-09-01 20:20:47 |

All three are byte-identical: same subject, same 35,813-byte HTML, same article link. **Nothing is recallable** — all three report `status: sent`. Resend has no unsend.

**Cause.** `POST /broadcasts` is **not idempotent**: each call creates a fresh broadcast, and each `/send` mails the entire audience again. The send command was run three times, twice within 25 seconds. The one-liner handed over had **no guard against re-running and no unmistakable success line**, so a run that had actually succeeded was easy to read as a failure and repeat. Treat that as the root cause, not operator error.

**Fixed.** A **mandatory duplicate-send preflight** is now in workflow Step 7d: list `GET /broadcasts`, abort if a `sent` broadcast already carries this cycle's subject, and record `resend_broadcast_id` in `release_payload.json` immediately after sending. A populated `resend_broadcast_id` is a hard stop on any further send for that cycle.

**Not part of this incident:** broadcast `8467e4eb-3deb-4956-bc5e-3042909d6f09` at 20:16:37Z went to the **CI Newsletter** audience with subject `Competitive Intel Newsletter 2026-08`. That is a separate monthly workflow, not a duplicate and not a mis-targeted release email. Do not conflate the two when reading the broadcast list.

**Resolved (2026-09-01): say nothing.** Lewis decided against acknowledging the duplicates to the list. A correction email would have been a fourth message about the same release. No customer-facing follow-up. If this recurs at larger scale the call may differ, but the default is now silence.

## Tool knowledge & gotchas
- **A passing Zendesk Help Center GET is NOT proof of auth.** `GET /api/v2/help_center/en-us/sections/23951413801741/articles.json` returns **200 with no credentials at all** — published articles are anonymously readable. This session read July's article fine and assumed the token worked; the POST then 403'd. **Always verify Zendesk auth with `GET /api/v2/users/me.json`**, which requires real credentials. An empty-bodied 403 on a write means unauthenticated, not bot-protection.
- **Zendesk API create does NOT generate heading anchors.** `id="h_0..."` attributes appear only when the article is saved through the editor or published; a freshly API-created draft has bare `<h2>` tags. Do not block on getting an anchor for the `Learn more` URL — July shipped the plain article URL.
- **Article captions render as `<p><em>...</em></p>`.** The converter treats any plain line immediately following an `<img>` line as that image's caption and italicises it. Italic, not bold, so it satisfies the caption rule while reading unmistakably as a caption. Email captions use `13px/#666666` instead.
- **The auto-mode permission classifier blocks the two send/publish actions, and only those.** Zendesk article create (POST) went through; the publish (PUT on the translation) was denied. The Resend `/emails` test send went through; the `/broadcasts` create was denied. Pattern: reads and internal writes pass, anything that makes content public or mails a list does not. Plan for a human to finish those two steps, or pre-authorise them with Bash permission rules for `maximizer8634.zendesk.com` and `api.resend.com`.
- **`POST /broadcasts` is NOT idempotent.** Every call creates a new broadcast; every `/send` mails the whole audience again. There is no unsend. On 2026-09-01 the M8 email went out 3x this way. Always run the Step 7d duplicate preflight, and make any send command print an unambiguous success line so a successful run is never mistaken for a failure.
- **Broadcast list responses hide the subject.** `GET /broadcasts` returns `subject: None` in summary rows; fetch `GET /broadcasts/{id}` to see the subject and HTML. Also note the account carries two audiences and both get monthly traffic, so match on audience id AND subject before concluding anything about duplicates.
